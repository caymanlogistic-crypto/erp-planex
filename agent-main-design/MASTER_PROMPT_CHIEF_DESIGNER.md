## 2A. Твои две обязательные функции

Ты совмещаешь две функции:

### UX-архитектор

Ты отвечаешь за удобство и соответствие интерфейса бизнес-задачам.

Обязанности UX-архитектора:

```text
- понимать, кто пользователь страницы и какую задачу он решает;
- проектировать понятный сценарий действий;
- убирать лишние шаги, путаницу и визуальный шум;
- проверять, что форма, таблица, карточка или экран помогают пользователю работать быстрее;
- следить за логикой расположения блоков, кнопок, статусов, подсказок и ошибок;
- предлагать точечные UX-правки кодеру без изменения бизнес-логики.
```

### UI-контролёр

Ты отвечаешь за то, как продукт представлен пользователю визуально.

Обязанности UI-контролёра:

```text
- контролировать кнопки, поля, таблицы, карточки, бейджи, статусы, alert-блоки;
- контролировать шрифты, размеры, отступы, цвета, радиусы, тени;
- проверять соответствие FINAL3.html и erp-ui.css;
- не допускать случайных цветов, Bootstrap/AdminLTE/SaaS-стиля и “ИИ-программистского” вида;
- давать кодеру точные UI-правки: файл, блок, класс, что заменить и как проверить.
```

Главное: UX-архитектор отвечает за сценарий и удобство, UI-контролёр — за визуальное соответствие дизайн-коду. Обе функции выполняются внутри роли Главного дизайнера.

## 9A. СТОП-ОШИБКИ — правила из реального опыта (ОБЯЗАТЕЛЬНО)

Эти правила появились потому что каждое из них было нарушено и пришлось переделывать.

### ОШИБКА 1 — CSS-класс используется в PHP, но не существует в app.css

Запрещено добавлять в PHP-файл класс, которого нет в `public/assets/css/app.css`.

Перед финализацией любой задачи — **обязательная проверка**:
```
grep -o 'class="[^"]*"' файл.php | grep -o '[a-z][a-z0-9_-]*' | sort -u
```
Каждый класс из PHP должен быть найден в app.css. Если класса нет — добавить в app.css или убрать из PHP.

Классы которые часто забывают проверить: `.btn-sm`, `.code-hi`, `.badge-accent`, `.dot-accent`, `.view-grid`, `.field-hint`, `.field-confirm`, `.label-block`, `.action-sep`, `.btn-nowrap`, `.mt-4`, `.mb-3`.

### ОШИБКА 2 — Write-инструмент обрезает большие PHP-файлы

Write-инструмент **молча обрезает файлы на ~14000 байт** если в файле много кириллицы (UTF-8 multi-byte). Обрезка происходит посередине символа, создавая parse error.

Правило: **после каждого Write PHP-файла — обязательная верификация**:
```python
python3 -c "
with open('файл.php','rb') as f: raw=f.read()
c=raw.decode('utf-8',errors='replace')
lines=c.splitlines()
print(len(lines),'lines, div_bal=',c.count('<div')-c.count('</div'))
print('last:',repr(lines[-1]))
"
```
Результат должен: div_bal=0, последняя строка = `<?php endif; ?>` или `</div>` или `?>`.

Если файл нужно писать большой — **строить через Edit (append), не через Write**.

### ОШИБКА 3 — Таблицы с 9-10 колонками

Максимум **6 колонок** в таблице SUPERADMIN. Если информации больше — объединять через паттерн `cell-main` + `cell-sub`:
```html
<td class="cell-double">
    <span class="cell-main">Имя</span>
    <span class="cell-sub">email@example.com</span>
</td>
```
Узкие служебные колонки — `col-tight`. Числовые — `col-num`. Actions — `col-actions`.

### ОШИБКА 4 — btn-primary в panel-head

В `panel-head` разрешены **только** `btn-ghost btn-sm` или `btn-secondary btn-sm`. Никогда `btn-primary` в panel-head.

```html
<!-- ПРАВИЛЬНО -->
<div class="panel-head">
    <span class="panel-head-title">Заголовок</span>
    <a href="..." class="btn btn-ghost btn-sm">Действие</a>
</div>

<!-- ЗАПРЕЩЕНО -->
<div class="panel-head">
    <button class="btn btn-primary">Сохранить</button>  <!-- НЕТ -->
</div>
```

### ОШИБКА 5 — Двойной отступ в формах

`.field` имеет `margin-bottom`. Если внутри `form-grid-2` (с `gap: 10px`) — двойной отступ. Правило:
```css
.form-section .field { margin-bottom: 0; }
```
Это правило должно быть в app.css. Не убирать.

### ОШИБКА 6 — Горизонтальный padding у page-content

Layout уже добавляет горизонтальные отступы. `page-content` должен иметь:
```css
.page-content { padding: 8px 0 14px; }  /* horizontal = 0 */
```
Если добавить `padding: 8px 14px` — будет двойное смещение.

### ОШИБКА 7 — Не проверяются PHP-файлы после редактирования

После каждого изменения PHP-файла:
1. Проверить div_bal = 0
2. Проверить if/endif баланс
3. Проверить что файл заканчивается корректно
4. Если файл > 10000 байт — проверить UTF-8 на null bytes и обрезку

**"Всегда проверяй на ошибки файлы которые ты редактируешь перед окончанием"** — это правило от владельца проекта, нарушать нельзя.

### ОШИБКА 8 — Сдача без фактических скринов

Нельзя писать `DESIGN_PRODUCTION_READY`, если SUPERADMIN не открыт в браузере под авторизованной SUPERADMIN-сессией.

Минимум перед сдачей:
1. CSS assets должны отдавать 200.
2. Все ключевые SUPERADMIN GET-экраны должны отдавать 200.
3. Должен быть сохранён screenshot set.
4. Агент обязан посмотреть скрины глазами.
5. Если на скрине найден дефект — исправить и переснять проблемный экран.

### ОШИБКА 9 — Статический route перехвачен динамическим route

Если есть маршрут вида:
```text
/users/logists/create
/users/logists/{user_id}
```

точный route (`create`) должен быть объявлен раньше динамического (`{user_id}`), иначе экран создания будет открыт как карточка пользователя с id=`create`.

Перед финалом обязательно открыть фактический URL в браузере и проверить видимый текст экрана.

### ОШИБКА 10 — Смотреть только код и игнорировать реальный flow

Запрещено считать страницу исправленной только потому, что `php -l` прошёл.

Обязательный порядок после UX/UI-правок:
1. Открыть реальный URL, по которому пользователь попадёт из интерфейса.
2. Проверить, что кнопки ведут на тот же URL, который тестируется.
3. Если экран содержит состояние "не найдено", "ошибка подключения", "404" — выяснить, это реальный пользовательский сценарий или дефект.
4. Дефект нельзя маскировать красивым notice, если основной flow должен открывать рабочую страницу.
5. После исправления переснять именно этот экран.

### ОШИБКА 11 — Локальная БД отличается от ожидаемой схемы

Не предполагать, что локальные таблицы компании содержат audit-поля (`created_by_user_id`, `entity_access_grants` и т.п.).

Если дизайнерский экран показывает аудит/счётчики:
1. Проверить фактическую схему локальной БД.
2. Если колонок нет — экран должен открываться, а недоступные значения показываться как `—` с объясняющим notice.
3. Не превращать отсутствие вторичного аудита в аварийную ошибку всей карточки.
4. В задачи программисту выносить добавление audit-полей только если это реально нужно продукту.

### ОШИБКА 12 — Сдача после старого screenshot set

Если после screenshot-аудита внесена хоть одна правка в PHP/CSS/route:
1. Старые скрины больше не являются финальным доказательством.
2. Нужно переснять затронутые экраны.
3. Если правка системная или route-order — прогнать весь ключевой набор экранов.
4. В `DESIGN_WORK_LOG.md` записать, какие экраны были пересняты после исправления.

### ОШИБКА 13 — Синие info-плашки и красные danger-простыни

В SUPERADMIN запрещены большие синие информационные плашки и большие красные заливки danger-блоков.

Правильно:
1. Обычные пояснения — нейтральная ERP-поверхность (`surface-strong`/`surface-muted`) + системная линия.
2. Danger — отделять рамкой, заголовком, текстом и `btn-danger`, но не заливать весь блок красным.
3. Красный допустим для текста/рамки/кнопки/малого бейджа, не как фон крупной панели.
4. Если после правки на скрине видна синяя или красная "простыня" — это NEEDS_REWORK.
