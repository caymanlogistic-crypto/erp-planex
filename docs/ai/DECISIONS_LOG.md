# ERP PLANEX — DECISIONS_LOG

## DECISION-0032 — Технические правила SUPERADMIN Companies Registry

### Решение
Для первого кодового модуля `SUPERADMIN Companies Registry` владелец утвердил технические детали создания экспедитора.

Поля, которые `SUPERADMIN` вводит при создании экспедитора, на первом этапе соответствуют базовому стандарту текущего контрагента / клиента:
- `name` — наименование, обязательное поле;
- `inn` — ИНН, обязательное поле;
- `kpp` — КПП;
- `ogrn` — ОГРН;
- `legal_address` — юридический адрес;
- `physical_address` — фактический адрес;
- `contact_person` — контактное лицо;
- `contact_phone` — телефон;
- `contact_email` — email;
- `status` — статус;
- `comments` — комментарий.

Экспедитор / компания в SUPERADMIN должен быть отдельной сущностью / таблицей реестра SUPERADMIN и не должен использовать локальную таблицу подрядчиков.

Имя локальной БД генерируется автоматически из `ID компании`. SUPERADMIN не вводит имя БД вручную.

Storage-папка компании генерируется / называется по `ID компании`.

`slug/key` не является источником истины для генерации имени локальной БД или storage-папки в первом Companies Registry implementation. Старые упоминания slug/key для путей и БД считаются superseded в этой части.

### Причина
Владелец подтвердил, что для старта достаточно стандартных реквизитных полей как у контрагента, но экспедитор должен быть отдельной сущностью SUPERADMIN. Генерация от ID снижает риск проблем с переименованием slug/кода компании и исключает ручной ввод технических имён.

### Статус
active

## DECISION-0031 — Модель onboarding экспедитора и локальной ERP

### Решение
Экспедитор в ERP PLANEX — это отдельная локальная ERP / компания, создаваемая `SUPERADMIN`.

Создание экспедитора выполняется автоматически одной операцией из SUPERADMIN и включает:
- запись в центральной БД SUPERADMIN;
- создание отдельной локальной БД;
- создание отдельной storage-папки для загруженных документов.

Кодовая база общая. PHP/JS/CSS/скрипты/миграции не копируются в папку экспедитора.

Главный пользователь экспедитора — это роль `Руководитель`. Он создается `SUPERADMIN` отдельным действием после создания экспедитора, хранится в центральной БД, привязывается к экспедитору, входит через общий логин и после входа попадает в локальную ERP своего экспедитора.

Локальные пользователи экспедитора хранятся в локальной БД экспедитора. Первый локальный пользовательский сценарий: `Руководитель` создает пользователя с ролью `Логист`.

Клиенты и подрядчики ведутся как отдельные справочники, таблицы и формы. Общая таблица `counterparties` с типом на первом этапе не используется.

Термины первого этапа: `клиент` и `подрядчик`. Отдельный термин `перевозчик` не вводится.

### Причина
Владелец утвердил путь развития системы: сначала SUPERADMIN создает экспедитора, затем главного пользователя, затем внутри локальной ERP создается логист, который ведет клиентов, подрядчиков, транспорт, водителей и связки.

### Статус
active

## DECISION-0033 — Модель главного пользователя экспедитора (Руководитель)

### Решение

Утверждена минимальная архитектура для главного пользователя экспедитора.

**Хранение:**
- Главный пользователь (`Руководитель`) хранится в центральной БД SUPERADMIN в отдельной таблице `company_users`.
- Отдельная таблица от `superadmin_users`, потому что у них разный scope: пользователь SUPERADMIN управляет всеми компаниями, а company_user привязан к одной компании.
- Локальные пользователи (Логист и др.) будут храниться в локальной БД компании — это следующий модуль.

**Таблица: `company_users`**

| Поле | Тип | Обязательное | Назначение |
|------|-----|-------------|------------|
| `id` | INT UNSIGNED AUTO_INCREMENT | Да | Первичный ключ |
| `company_id` | INT UNSIGNED | Да | FK → `companies.id` |
| `full_name` | VARCHAR(255) | Да | Полное имя |
| `login` | VARCHAR(100) | Да | Логин для входа |
| `email` | VARCHAR(255) | Нет | Email (опционально) |
| `phone` | VARCHAR(50) | Нет | Телефон (опционально) |
| `password_hash` | VARCHAR(255) | Да | Хэш пароля (bcrypt, password_hash()) |
| `role` | VARCHAR(50) | Да | `company_owner` — системный код роли |
| `status` | VARCHAR(20) | Да | `active` / `blocked` |
| `comments` | TEXT | Нет | Комментарий SUPERADMIN |
| `created_at` | TIMESTAMP | Да | Дата создания |
| `updated_at` | TIMESTAMP | Да | Дата обновления |

**Ключевые архитектурные решения:**

1. **Роль Руководителя**: системный код `company_owner`, human-readable `Руководитель`.
2. **Связь с компанией**: `company_id` → `companies.id`, FK с ON DELETE CASCADE. Один руководитель принадлежит одной компании.
3. **Логин**: отдельное поле `login`, не email. Email опциональный, не используется как логин на первом этапе.
4. **Пароль**: хранится только `password_hash` (PHP `password_hash()` bcrypt). Открытый пароль не хранится в БД. Временный пароль генерируется SUPERADMIN или системой и показывается один раз после создания.
5. **Дублирование**: одна компания → один активный Руководитель. Проверка на уровне приложения: если `company_users` уже содержит активную запись с `role = 'company_owner'` для этого `company_id`, создание блокируется. В companies list показывается статус: «Руководитель создан» или кнопка «Создать Руководителя».
6. **Доступ**: Руководитель не имеет доступа к SUPERADMIN, не видит другие компании.

**Минимальные обязательные поля при создании:**
- `full_name` — обязательное
- `login` — обязательное
- `password` — системно генерируется, если не введён вручную

**Что НЕ реализуется сейчас:**
- Полноценная авторизация/сессии/login/logout
- Email-отправка
- Reset password flow
- Сложные permissions UI
- Редактирование Руководителя
- Блокировка/удаление Руководителя
- Логист, клиенты, подрядчики

### Причина

Для создания цепочки onboarding: SUPERADMIN → компания → Руководитель → Логист. Руководитель — обязательный следующий шаг после Companies Registry.

### Статус

active

## DECISION-0016 — Проектные KILO-агенты вместо внешнего координатора

### Решение
Агентская сеть ERP PLANEX перенесена внутрь KILO. Вместо внешнего ChatGPT-координатора используются 4 проектных KILO-агента:

- `erp-architect` (primary, default_agent) — главный координатор;
- `erp-uiux-designer` (primary/selectable) — UI/UX-дизайнер;
- `erp-coder` (primary/selectable) — исполнитель разработки;
- `erp-qa-tester` (primary/selectable) — тестировщик.

Все 4 агента должны быть доступны в выпадающем списке KILO. `subagent`-режим не используется для этих ролей, потому что интерфейс KILO показывает только primary/selectable agents.

Все агенты определены в `.kilo/agent/*.md`. Главный режим — `erp-architect` (установлен как `default_agent` в `kilo.jsonc`).

Пользователь в основном общается с `erp-architect`. Архитектор делегирует задачи остальным агентам через `task` tool.

Рабочий цикл:
```text
Владелец → erp-architect → erp-uiux-designer / erp-coder / erp-qa-tester → erp-architect → принятие / второй круг
```

### Причина
Переход от внешнего ChatGPT-координатора к внутренним проектным KILO-агентам упрощает агентный цикл: все роли работают в одной среде KILO, контекст не теряется между чатами, задачи и результаты передаются внутри одной сессии.

### Статус
active

## DECISION-0017 — UI-страницы реализуются через MD-шаблоны дизайнера

### Решение
При создании или изменении любой страницы ERP PLANEX сначала должен работать `erp-uiux-designer`, если задача затрагивает интерфейс, пользовательский сценарий, форму, таблицу, карточку сущности, навигацию, статусы, модалки, inspector, empty/loading/error states или расположение блоков.

Дизайнер обязан создать или обновить MD-шаблон страницы в:

```text
docs/ui/pages/
```

MD-шаблон страницы является источником истины для кодера и QA.

Рабочий цикл UI-задачи:

```text
erp-architect → erp-uiux-designer → erp-coder → erp-qa-tester → erp-architect
```

Кодер реализует UI строго по актуальному MD-шаблону страницы.

QA проверяет соответствие реализации этому шаблону.

Архитектор не принимает UI-задачу как `DONE`, если MD-шаблон отсутствует, устарел или реализация ему не соответствует.

### Причина
ERP PLANEX должна развиваться единообразно. Кодер не должен сам придумывать внешний вид, структуру страницы, классы, layout и UX-поведение. MD-шаблон страницы снижает хаос, упрощает проверку и сохраняет дизайн-код в документации.

### Статус
active

## DECISION-0020 — Windows PowerShell command rules

### Решение

Зафиксировать обязательные правила выполнения команд в Windows PowerShell для всех агентов проекта.

Конкретные правила:
1. Проект работает на Windows. Команды выполняются в Windows PowerShell 5.1, которая не является Linux shell.
2. **Запрещено** использовать Linux-style `curl` синтаксис в PowerShell: `curl` — это alias для `Invoke-WebRequest`, флаги `-s`, `-o NUL`, `-w` несовместимы.
3. Для HTTP-проверок использовать `Invoke-WebRequest` с `-UseBasicParsing` или `cmd.exe /c curl.exe`.
4. Для проверки HTTP 4xx/5xx использовать try/catch, чтобы PowerShell не прерывал выполнение.
5. В спорных случаях для Git использовать `cmd.exe /c "git ..."` или `git --no-pager`.
6. Команды должны быть проверяемыми и не должны зависать.
7. Если команда сломалась из-за оболочки — это не ACCEPTED, нужно повторить корректной командой.
8. Shell-ошибки из-за несовместимости — tooling/runtime issues, не app failures.

Правила зафиксированы в отдельном документе: `docs/ai/WINDOWS_POWERSHELL_COMMAND_RULES.md`.

Ссылки добавлены в: `KILO_PROJECT_RULES.md`, `QA_CHECKLIST.md`, `DEEPSEEK_CODER_RULES.md`, `TASK_TEMPLATE.md`.

### Причина

Во время QA SUPERADMIN Stage 1 (2026-06-12) агент использовал Linux-style `curl` команду в PowerShell:
```
curl -s -o NUL -w "%{http_code}" http://127.0.0.1:8015/superadmin
```
PowerShell воспринял `curl` как alias для `Invoke-WebRequest`, команда сломалась, QA-проверка зависла/остановилась. Чтобы предотвратить повторение, правила зафиксированы как системное требование.

### Статус

active

## DECISION-0021 — Схема центральной БД SUPERADMIN

### Решение

Утверждена точная архитектурная схема центральной БД SUPERADMIN. Создан документ `docs/architecture/SUPERADMIN_DATABASE.md`.

**Таблицы:**

1. `companies` — центральный реестр компаний/локальных ERP. Поля: id, key (уникальный slug, неизменяем), name, short_name, entity_type, status (active/inactive/suspended/provisioning), folder_path, db_identifier (только имя БД, НЕ пароль), storage_path, settings_json (JSON), created_at, updated_at. 5 индексов.

2. `features` — реестр функций. Поля: id, code (уникальный, конвенция `type.name`), name, type (module/page/report/custom_report/action/integration/ui_block), description, parent_code (иерархия), is_system, is_active, sort_order, created_at, updated_at. 6 индексов. Само-ссылка FK: parent_code → code.

3. `company_features` — связка компаний и функций (feature toggles). Поля: id, company_id (FK→companies), feature_code (FK→features), is_enabled, enabled_from, enabled_until, notes, created_at, updated_at. 6 индексов. Уникальность (company_id, feature_code). Default-deny: если записи нет — функция недоступна.

4. `superadmin_users` — пользователи SUPERADMIN (отдельные от локальных users). Поля: id, name, email (уникальный), password_hash (bcrypt, cost ≥ 12), role (admin/operator/viewer), is_active, last_login_at, last_login_ip, created_at, updated_at. 4 индекса.

**Ключевые архитектурные решения:**
- Все таблицы: InnoDB, utf8mb4, utf8mb4_unicode_ci, timestamps created_at/updated_at.
- DB credentials (пароли, хосты, порты, пользователи) **никогда не хранятся в таблице companies или любой другой таблице БД**. Только логический `db_identifier`. Реальные credentials — в локальном `.env` или внешнем хранилище секретов.
- Feature toggles: модель default-deny (компания не имеет доступа к функции, пока нет явной записи с is_enabled=1).
- Конвенция кодов feature: `type.name` (например, `module.trips`, `page.finance_report`, `report.monthly_pnl`).
- Статусная модель companies: provisioning → active, active ↔ suspended, active ↔ inactive.

### Причина

Перед созданием миграций нужна точная спецификация, чтобы кодер не придумывал схему на ходу, а следовал утверждённому архитектурному документу.

## DECISION-0023 — Системные правила UI-процесса ERP PLANEX

## DECISION-0024 — UI Production Loop для важных UI-экранов

### Решение

Для важных UI-экранов ERP PLANEX вводится обязательный UI Production Loop:

```text
Architect intake
→ Designer production handoff
→ Architect handoff review
→ Coder implementation
→ Formal QA
→ Architect pre-owner review
→ repeat designer/coder/QA cycle if not enough
→ Owner visual review
→ commit only after owner approval
```

Ключевые правила:

1. Важный UI нельзя отдавать кодеру без production-grade handoff от `erp-uiux-designer`.
2. `erp-architect` обязан выполнить handoff review до передачи кодеру.
3. Если handoff общий, противоречивый, устаревший, содержит `REJECTED` как актуальный статус или допускает разные трактовки, задача возвращается дизайнеру со статусом `NEEDS_DESIGNER_REWORK`.
4. `erp-coder` обязан вернуть `BLOCKED: NEEDS_DESIGNER_REWORK`, если handoff слабый, отсутствует, противоречит design-code/PAGE_PATTERN или не указывает точные sections/classes/tokens.
5. `Formal UI QA: PASS` не является visual acceptance.
6. После QA `erp-architect` обязан выполнить pre-owner review.
7. Если результат всё ещё похож на demo/foundation/showcase/web-page/SaaS-dashboard или не соответствует master UI-kit, владелец не получает экран как готовый; запускается повторный цикл designer/coder/QA.
8. Owner visual review запускается только после того, как агентская цепочка сама довела экран максимально близко к master UI-kit.
9. Commit UI-экрана разрешён только после явного owner approval.

### Причина

После двух rework `/superadmin` стало ясно, что прежние правила закрывали отдельные симптомы, но не закрывали процесс: designer мог выдать общий handoff, architect мог слишком рано передать задачу кодеру, coder формально реализовывал слабую спецификацию, QA давал Formal PASS, а владелец затем визуально видел несоответствие master UI-kit.

Нужен производственный UI-конвейер с обязательными gate points до кодера, после QA и перед owner visual review.

### Статус

active

## DECISION-0034 — Модель локального пользователя компании (Логист)

### Решение

Утверждена минимальная архитектура для локального пользователя компании — Логиста.

**Хранение:**
- Логист хранится в локальной БД компании (`erp_company_{id}`), в таблице `users`.
- Не хранится в центральной БД SUPERADMIN, не является `company_users`.
- Каждая компания имеет свою таблицу `users` в своей локальной БД.

**Таблица: `users` (локальная БД компании)**

| Поле | Тип | Обязательное | Назначение |
|------|-----|-------------|------------|
| `id` | INT UNSIGNED AUTO_INCREMENT | Да | Первичный ключ |
| `full_name` | VARCHAR(255) | Да | Полное имя |
| `login` | VARCHAR(100) | Да | Логин для входа, уникален в пределах локальной БД |
| `email` | VARCHAR(255) | Нет | Email (опционально) |
| `phone` | VARCHAR(50) | Нет | Телефон (опционально) |
| `password_hash` | VARCHAR(255) | Да | Хэш пароля (bcrypt, password_hash()) |
| `role_code` | VARCHAR(50) | Да | `logist` — системный код роли |
| `status` | VARCHAR(20) | Да | `active` / `blocked` |
| `created_at` | TIMESTAMP | Да | Дата создания |
| `updated_at` | TIMESTAMP | Да | Дата обновления |

**Индексы:**
- `PRIMARY KEY` (`id`)
- `UNIQUE KEY uk_login` (`login`)

**Ключевые архитектурные решения:**

1. **Роль Логиста**: системный код `logist`, human-readable `Логист`.
2. **Привязка к компании**: Логист находится в локальной БД компании, привязка через сам факт нахождения в этой БД. Дополнительный `company_id` в таблице `users` локальной БД не требуется.
3. **Логин**: отдельное поле `login`, не email. Email опциональный, не используется как логин. Уникальность логина в пределах локальной БД компании через UNIQUE KEY.
4. **Пароль**: хранится только `password_hash` (PHP `password_hash()` bcrypt). Открытый пароль не хранится в БД. Временный пароль генерируется системой и показывается один раз после создания.
5. **Доступ**: Логист не имеет доступа к SUPERADMIN, не видит другие компании, не может создавать других пользователей.
6. **Создатель**: Логиста создаёт Руководитель (`company_owner`) внутри своей локальной ERP.

**Минимальные обязательные поля при создании:**
- `full_name` — обязательное
- `login` — обязательное
- `password` — системно генерируется, если не введён вручную

**Временный механизм контекста компании:**
- Поскольку полноценная авторизация ещё не реализована, для функциональной проверки используется параметр `?company_id=N` в URL.
- Страницы модуля: `/company/logists?company_id=N`, `/company/logists/create?company_id=N`.
- Это временное решение; при реализации auth/session будет заменено на контекст из сессии.

**Что НЕ реализуется сейчас:**
- Полноценная авторизация/сессии/login/logout
- Email-отправка
- Reset password flow
- Редактирование/блокировка/удаление логиста
- Клиенты, подрядчики, транспорт, водители, экипажи, рейсы
- Сложная система меню и навигации в локальной ERP
- UI polish, pagination, сложные фильтры

### Причина

Для продолжения цепочки onboarding: SUPERADMIN → компания → Руководитель → Логист. Логист — обязательный следующий шаг после Руководителя.

### Статус

active

## DECISION-0039 — Модель локального справочника экипажей (crews)

### Решение

Утверждена минимальная архитектура для локального справочника экипажей компании.

**Ключевое правило:** ЭКИПАЖ = Подрядчик + Машина + Водитель. Экипаж — жёсткая комбинация трёх сущностей. Водители и транспорт могут существовать отдельно в справочниках до создания экипажа.

**Хранение:**
- Экипажи хранятся в локальной БД компании (`erp_company_{id}`), в таблице `crews`.
- Не хранятся в центральной БД SUPERADMIN.
- Экипажи разных компаний физически разделены разными локальными БД.
- Экипаж не является центральной SUPERADMIN-сущностью.

**Таблица: `crews` (локальная БД компании)**

| Поле | Тип | Обязательное | Назначение |
|------|-----|-------------|------------|
| `id` | INT UNSIGNED AUTO_INCREMENT | Да | Первичный ключ |
| `contractor_id` | INT UNSIGNED | Да | Ссылка на `contractors.id` |
| `vehicle_id` | INT UNSIGNED | Да | Ссылка на `vehicles.id` |
| `driver_id` | INT UNSIGNED | Да | Ссылка на `drivers.id` |
| `status` | VARCHAR(20) | Да | `active` / `inactive` |
| `comments` | TEXT | Нет | Комментарий |
| `created_at` | TIMESTAMP | Да | Дата создания |
| `updated_at` | TIMESTAMP | Да | Дата обновления |

**Индексы:**
- `PRIMARY KEY` (`id`)
- `UNIQUE KEY uk_crew` (`contractor_id`, `vehicle_id`, `driver_id`) — уникальная комбинация в пределах локальной БД

**Ключевые архитектурные решения:**

1. **Обязательные поля при создании**: `contractor_id`, `vehicle_id`, `driver_id` (все три select в форме).
2. **Уникальность комбинации**: contractor_id + vehicle_id + driver_id уникальна в пределах локальной БД. Дублирование блокируется с сообщением «Такой экипаж уже существует в этой компании».
3. **Статусы**: `active`, `inactive`. По умолчанию `active`.
4. **Связи**: contractor_id → contractors.id, vehicle_id → vehicles.id, driver_id → drivers.id. Жёсткие FK не создаются на первом этапе (для упрощения), но проверка существования выполняется на уровне приложения.
5. **Привязка к компании**: через сам факт нахождения в локальной БД. Дополнительный `company_id` в таблице `crews` не требуется.
6. **Контекст компании**: временно через `?company_id=N` в URL.
7. **Правило истории**: рейс в будущем будет ссылаться на `crew_id`. Для защиты истории рейса желательно хранить snapshot (название подрядчика, ФИО водителя, номер машины).
8. **Один водитель — несколько экипажей**: разрешено (с разными машинами):
   - Экипаж 1: Иванов + А999АА99
   - Экипаж 2: Иванов + И999ПП99
9. **Одна машина — несколько экипажей**: разрешено, если та же машина с разными водителями.

**Предусловия для создания экипажа (blocking dependencies):**
- Минимум 1 активный подрядчик в `contractors`
- Минимум 1 активный водитель в `drivers`
- Минимум 1 активный транспорт в `vehicles`
- Если чего-то нет — форма показывает blocking state: «Сначала создайте подрядчика», «Сначала создайте водителя», «Сначала создайте транспорт».

**Что НЕ реализуется сейчас:**
- Редактирование экипажа
- Удаление экипажа
- Назначение экипажа на рейс
- Рейсы, заявки, документы
- Графики работы экипажей
- Загрузка файлов
- Pagination, сложные фильтры
- Снапшоты данных экипажа для истории рейсов

### Причина

Для завершения справочного фундамента компании: после клиентов, подрядчиков, водителей и транспорта — финальный модуль «Экипажи», закрывающий справочный блок.

## DECISION-0040 — Модель управления компанией и Руководителем в SUPERADMIN

### Решение

После завершения справочного фундамента (REFERENCE_BLOCK_ACCEPTED) владелец выявил пробел: создание экспедитора и Руководителя есть, но нет управления ими. Утверждена минимальная модель управления.

#### 1. Управление компанией (Company Management)

**Маршруты:**
- `GET /superadmin/companies/{id}` — карточка компании (view)
- `GET /superadmin/companies/{id}/edit` — форма редактирования
- `POST /superadmin/companies/{id}/edit` — сохранение изменений

**Карточка компании (view):**
- Все поля: название, ИНН, КПП, ОГРН, юр. адрес, факт. адрес, контактное лицо, телефон, email, статус, комментарии
- Технические поля: local DB name, storage path, provisioning status, error_message (если есть)
- Информация о Руководителе (если создан): ФИО, логин, email, телефон, статус, ссылка на управление
- Кнопки действий: «Редактировать», «← К реестру»

**Редактирование компании:**
- Поля: name*, inn*, kpp, ogrn, legal_address, physical_address, contact_person, contact_phone, contact_email, status, comments
- Обязательные: name, inn
- Проверки: name required, inn required, duplicate inn среди других companies блокируется
- Статусы в select: active, inactive, blocked, archived
- Нельзя менять: db_identifier, storage_path, provisioning fields (folder_path, settings_json)
- Invalid company_id → 200 с сообщением «Компания не найдена» (не 500)

**Управление статусом компании (безопасное):**
- Доступные статусы: `active`, `inactive`, `blocked`, `archived`
- Статусы меняются через edit-form status select
- Никакой статус не вызывает физического удаления: локальной БД, storage, company_users, локальных справочников
- Проверка: db_identifier остаётся неизменным, storage_path остаётся неизменным

**Что запрещено:**
- Физически удалять локальную БД
- Физически удалять storage/companies/{id}/
- Удалять company_users
- Удалять локальные справочники
- Менять db_identifier
- Менять storage_path
- Менять provisioning поля

#### 2. Управление Руководителем (Owner Management)

**Маршруты:**
- `GET /superadmin/companies/{id}/owner` — карточка Руководителя (view)
- `GET /superadmin/companies/{id}/owner/edit` — форма редактирования
- `POST /superadmin/companies/{id}/owner/edit` — сохранение изменений
- `POST /superadmin/companies/{id}/owner/reset-password` — сброс пароля

**Карточка Руководителя (view):**
- Поля: ФИО, логин, email, телефон, роль, статус, комментарий, дата создания
- Кнопки: «Редактировать», «Сбросить пароля», «← К карточке компании»

**Редактирование Руководителя:**
- Поля: full_name*, login*, email, phone, status, comments
- Обязательные: full_name, login
- Проверки: full_name required, login required (латиница/цифры/подчёркивание), email опциональный с валидацией формата, duplicate login среди других company_users блокируется
- Статусы: active, blocked

**Сброс пароля Руководителя:**
- POST-запрос генерирует новый временный пароль (10 символов)
- Пароль хэшируется bcrypt и сохраняется в password_hash
- Временный пароль показывается один раз на странице результата
- Plaintext пароль не сохраняется в БД, логах, MD или git
- Результат: «Пароль сброшен. Новый временный пароль: ...»

**Проверки:**
- Один Руководитель на компанию (уже обеспечено существующей логикой)
- duplicate login блокируется
- Руководитель не получает SUPERADMIN-доступ
- Invalid company_id / missing owner → 200 с понятным сообщением (не 500)
- password_hash только bcrypt

#### 3. Обновление реестра компаний

В таблице `superadmin_companies.php` для компаний с Руководителем:
- Вместо текущей ссылки «Просмотреть» на `/superadmin/companies/{id}/create-owner` → ссылка «Карточка» на `/superadmin/companies/{id}`
- Кнопка «Создать Руководителя» остаётся для компаний без Руководителя

#### 4. Что НЕ реализуется сейчас

- auth/session
- реальный login
- email-отправка пароля
- удаление локальной БД
- удаление storage
- удаление справочников компании
- рейсы, документы, заявки, договора

- UI polish

### Причина

Владелец при ручной проверке справочного фундамента выявил, что экспедитор и Руководитель создаются, но отсутствует управление ими (редактирование, статусы, сброс пароля). Это критический пробел до передачи реальным пользователям.

### Статус

active
