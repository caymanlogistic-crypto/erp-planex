## Deployment-модель

Код общий, но каждая компания имеет:
- отдельную папку;
- отдельную БД;
- отдельный `/storage`;
- отдельный `.env`.

Пример:

```text
erp/
  superadmin/
  planex/
  company_a/
  company_b/
```

Одна локальная ERP = одно юридическое лицо.

Локальная ERP не должна иметь прямого доступа к данным другой локальной ERP.

SUPERADMIN может иметь максимальный доступ, но он должен быть явно отделён от локальных ролей.

## Локальная ERP

Локальная ERP — ERP конкретного юридического лица.

Одна локальная ERP = одна папка + одна БД + одно юридическое лицо.

В локальной ERP есть роль `Руководитель`.

## Роль “Руководитель”

`Руководитель` — локальный администратор ERP конкретной компании.

Он видит всё внутри своей компании, включая бухгалтерские данные.

Остальные роли пока не утверждены окончательно. Предварительно возможны:
- менеджер;
- логист;
- бухгалтер;
- оператор;
- просмотр.

Эти роли нельзя превращать в код без подтверждения владельца.

## Feature toggles и permissions

Доступ определяется двумя уровнями:

```text

+

```

Источник истины по features — центральная БД SUPERADMIN.

Локальная ERP использует локальный кэш доступных features, чтобы продолжать работать при временной недоступности SUPERADMIN.

Типы features:

```text
module
page
report
action
integration
ui_block
```

Запрещено добавлять новую страницу без `feature_code`.

Запрещено делать действия без `permission_code`.

Запрещено проверять только роль без проверки feature.

## Водители, машины и экипажи

Водители и машины могут существовать отдельно в справочнике подрядчика до создания экипажа.

Экипаж = Подрядчик + жёсткая пара Машина + Водитель.

Если тот же водитель едет на другой машине, создаётся новый экипаж.

Рейс должен ссылаться на `crew_id`.

Для защиты истории рейса желательно хранить snapshot:
- название подрядчика;
- ФИО водителя;
- номер машины.

## Первый бизнес-процесс

На первом этапе реализуется только линейная перевозка.

Цепочка:
1. Получаем заявку от клиента.
2. Создаём или выбираем клиента.
3. Заполняем карточку клиента.
4. Загружаем необходимые документы клиента.
5. Подписываем договор с клиентом по шаблону из системы или кастомный договор.
6. Создаём рейс.
7. Указываем загрузку, выгрузку, условия, клиента и связанную заявку.
8. Выбираем подрядчика.
9. Выбираем или создаём экипаж.
10. Выполняем рейс.
11. В будущем храним счета, оплаты, договоры, закрывающие документы, акты сверки.

На первом этапе не реализуется:
- полная бухгалтерия;
- полные акты сверки;
- сборные рейсы;
- глубокая проверка документов;
- сложные отчёты.

Сборный рейс резервируется в архитектуре, но не реализуется.

## Как писать промты KILO

Промт KILO должен быть конкретным.

Нельзя давать размытые задачи типа:

```text
делай ERP
```

Задача должна содержать:
- цель;
- список файлов, которые нужно прочитать;
- что именно сделать;
- что запрещено;
- какие проверки выполнить;
- какие MD-файлы обновить;
- нужен commit или нет;
- формат FINAL REPORT.

## Как принимать FINAL REPORT агента

FINAL REPORT должен содержать:
- статус;
- что сделано;
- какие файлы прочитаны;
- какие файлы созданы;
- какие файлы обновлены;
- проверки;
- git status;
- что не делалось;
- риски;
- вопросы владельцу;
- следующий шаг;
- обновлялся ли `ERP_PLANEX_CONTEXT_FOR_NEW_CHAT.md`, а если нет — почему.

Если агент не обновил логи, статус или этот файл при изменении контекста, задача не считается полностью закрытой.
