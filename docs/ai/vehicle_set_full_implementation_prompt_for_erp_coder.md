## Доменные правила, которые нужно реализовать

### 1. Типы комплектов

Поддерживаются 3 типа `vehicle_sets.set_type`:

- `single`
- `coupling`
- `road_train`

### 2. Допустимые unit_type по типу комплекта

Нужно реализовать следующую матрицу совместимости:

#### `single`
- основная единица: `single` ИЛИ `truck`
- дополнительная единица: отсутствует

#### `coupling`
- основная единица: `tractor`
- дополнительная единица: `semi_trailer`

#### `road_train`
- основная единица: `truck`
- дополнительная единица: `trailer`

### 3. Недопустимые комбинации

Нельзя сохранять:
- `single` + заполненная дополнительная единица
- `coupling` без `secondary_vehicle_unit_id`
- `road_train` без `secondary_vehicle_unit_id`
- `coupling`, если основная единица не `tractor`
- `coupling`, если дополнительная единица не `semi_trailer`
- `road_train`, если основная единица не `truck`
- `road_train`, если дополнительная единица не `trailer`
- одинаковую единицу в primary и secondary
- unit со статусом не `active`

## Что нужно сделать во фронтенде

### 1. Зависимость формы от `Тип комплекта`

На фронтенде нужно сделать динамическое поведение:

#### Для `single`
- скрыть/отключить поле дополнительной транспортной единицы;
- очистить значение secondary при переключении на `single`;
- показать подпись основной единицы в понятной форме;
- показать только набор документов для одиночной схемы.

#### Для `coupling`
- показать поле дополнительной единицы;
- primary select должен оставлять только `tractor`;
- secondary select должен оставлять только `semi_trailer`;
- подписи должны быть семантически корректны, например:
  - основная единица: тягач
  - дополнительная единица: полуприцеп

#### Для `road_train`
- показать поле дополнительной единицы;
- primary select должен оставлять только `truck`;
- secondary select должен оставлять только `trailer`;
- подписи должны быть семантически корректны, например:
  - основная единица: грузовик
  - дополнительная единица: прицеп

### 2. Фильтрация селектов

Варианты единиц должны фильтроваться по `vehicle_units.unit_type`.

Реализация должна быть такой, чтобы:
- не просто показывать ошибку после submit,
- а реально не предлагать пользователю неподходящие unit.

Если текущее наполнение селектов идёт общим списком активных `vehicle_units`, добавь в option data-атрибут типа (`data-unit-type`) и фильтруй на фронте.

### 3. Сброс невалидных значений

При смене `set_type`:
- если выбранная ранее primary единица больше не подходит — сбросить её;
- если выбранная ранее secondary единица больше не подходит — сбросить её;
- если secondary не нужен — очищать и отключать его.

### 4. Предопределённые документы

Правый блок `ДОКУМЕНТЫ` должен зависеть от типа комплекта.

Нужно визуально оставить блок в текущем стиле, но логически разделить документы:

#### Для основной единицы
Всегда нужен набор:
- СТС
- ПТС
- ОСАГО

#### Для дополнительной единицы
Нужен только если комплект не `single`.
Минимальный набор:
- СТС
- ПТС

Если в текущем проекте документная логика уже умеет работать с предопределёнными блоками — используй существующий паттерн.

Важно:
- не ломать multiple;
- не возвращать `accept`;
- не ломать текущую логику бейджей типа файла;
- не делать тяжёлую искусственную обработку выбора файла.

### 5. Custom documents

Блок произвольных документов должен остаться рабочим.

Нужно сохранить возможность:
- выбрать существующий тип документа,
- или ввести новый,
- прикрепить файл,
- добавить несколько пользовательских документов.

Не убирать и не ломать этот сценарий.

### 6. Клиентская валидация

На фронтенде нужна клиентская проверка:
- выбран `set_type`;
- выбрана primary единица;
- secondary обязателен для `coupling` и `road_train`;
- secondary запрещён для `single`;
- primary/secondary соответствуют правилам матрицы;
- primary != secondary;
- custom documents: если файл выбран, то должен быть указан тип или новый тип;
- если задан custom doc type, но файл не выбран — тоже ошибка;
- валидация не должна ломать обычный submit.

Если на проекте уже есть способ показа ошибок рядом с полями — использовать его.

## Что нужно сделать на бэкенде

### 1. Валидация совместимости

Главная серверная задача: перестать принимать любые сочетания `set_type` + unit_type.

Нужна серверная функция/логика уровня маршрута/сервиса, которая проверяет:
- существование выбранных unit;
- статус unit = `active`;
- соответствие матрице совместимости;
- обязательность/необязательность secondary;
- несовпадение primary/secondary.

Эта проверка должна быть обязательной, даже если фронт сломан или отключён.

### 2. Создание `vehicle_set`

После успешной валидации сохранить:
- `set_type`
- `primary_vehicle_unit_id`
- `secondary_vehicle_unit_id` (если нужен)
- `status`
- `comments`
- `created_by_user_id`
- `created_by_role`

Ничего не выдумывать сверх схемы из БД.

### 3. Сохранение предопределённых документов

Это очень важный момент.

Предопределённые документы должны сохраняться не абстрактно на `vehicle_set`, а по сущности, к которой они относятся.

То есть:

#### Документы основной единицы:
сохранять как
- `documents.entity_type = 'vehicle_unit'`
- `documents.entity_id = primary_vehicle_unit_id`

#### Документы дополнительной единицы:
сохранять как
- `documents.entity_type = 'vehicle_unit'`
- `documents.entity_id = secondary_vehicle_unit_id`

### 4. Сохранение custom documents

Произвольные документы комплекта сохранять как:
- `documents.entity_type = 'vehicle_set'`
- `documents.entity_id = new vehicle_set id`

То есть логика такая:
- predefined docs > на unit
- custom docs > на set

### 5. Типы документов

Использовать `document_types`.

Если тип предопределённый:
- использовать существующий `document_type_id`, если найден;
- если по текущей архитектуре проекта допустимо авто-создание предопределённого типа — делать консистентно с существующей логикой;
- не плодить дубли бессистемно.

Если custom type введён вручную и его нет:
- создать запись в `document_types` для `entity_type = 'vehicle_set'`, `category = 'custom'`, если это соответствует текущему паттерну проекта.

### 6. Загрузка файлов

Нужно сохранить текущую рабочую файловую механику:
- multiple не ломать;
- не ломать хранилище;
- не ломать mime/original_name/stored_name/relative_path/file_size;
- не менять бекэнд-проверки расширений, если они уже есть;
- не переносить файлы в “временную” архитектуру.

### 7. Ошибки

При серверной ошибке/валидации страница должна:
- вернуться на форму создания;
- показать ошибки пользователю;
- сохранить старые значения формы;
- не терять уже введённые текстовые поля;
- не ломать разметку.

## ВНИМАНИЕ: сверка с реальной схемой обязательна

Этот документ может содержать плановые или промежуточные формулировки. При любых правках `driver_vehicle_blocks` / `crews` приоритет имеет реальная схема, выгруженная 2026-06-26: `driver_vehicle_blocks` не содержит `vehicle_id`; `crews.vehicle_id` остаётся legacy-полем и заполняется из `vehicle_sets.primary_vehicle_unit_id`.
