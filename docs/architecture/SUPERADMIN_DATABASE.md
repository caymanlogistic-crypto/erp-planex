# ERP PLANEX — SUPERADMIN_DATABASE

## Назначение

Точная архитектурная спецификация центральной БД SUPERADMIN. Этот документ является источником истины для создания миграций и реализации доступа к данным SUPERADMIN.

Центральная БД SUPERADMIN — единая база данных, обслуживающая панель SUPERADMIN. Она НЕ используется локальными ERP напрямую. Локальные ERP имеют собственные БД и получают данные о доступных features через локальный кэш (см. `docs/architecture/FEATURE_TOGGLES.md`).

## Статус документа

**Stage 2 — проектирование.** Миграции ещё не созданы. Таблицы в MySQL не созданы. Этот документ — архитектурная спецификация для будущих миграций.

## Общие правила для всех таблиц

| Параметр | Значение |
|---|---|
| Движок | InnoDB |
| Кодировка | utf8mb4 |
| Collation | utf8mb4_unicode_ci |
| Timestamps | `created_at` / `updated_at` во всех таблицах |
| Именование PK | `id` INT UNSIGNED AUTO_INCREMENT |
| Именование FK | `{table}_id` |
| Soft delete | Не используется на Stage 2. При необходимости добавится позже. |

```text
┌──────────────────┐       ┌──────────────────────┐
│    companies     │       │      features        │
│──────────────────│       │──────────────────────│
│ id (PK)          │──┐    │ code (PK, VARCHAR)   │──┐
│ key (UNIQUE)     │  │    │ name                 │  │
│ name             │  │    │ type                 │  │
│ entity_type      │  │    │ description          │  │
│ status           │  │    │ parent_code (FK self)│  │
│ folder_path      │  │    │ is_system            │  │
│ db_identifier    │  │    │ is_active            │  │
│ settings_json    │  │    │ sort_order           │  │
│ created_at       │  │    │ created_at           │  │
│ updated_at       │  │    │ updated_at           │  │
└──────────────────┘  │    └──────────────────────┘  │
                       │                              │
                       │    ┌──────────────────────┐  │
                       │    │  company_features    │  │
                       │    │──────────────────────│  │
                       ├────│ company_id (FK)      │  │
                       │    │ feature_code (FK)    │──┘
                       │    │ is_enabled           │
                       │    │ enabled_from         │
                       │    │ enabled_until        │
                       │    │ notes                │
                       │    └──────────────────────┘
                       │
┌──────────────────────┐
│  superadmin_users   │
│──────────────────────│
│ id (PK)              │
│ name                 │
│ email (UNIQUE)       │
│ password_hash        │

│ last_login_ip        │

```

Примечание: `superadmin_users` не связана внешним ключом с `companies`, так как пользователь SUPERADMIN управляет всеми компаниями, а не принадлежит конкретной.

## Таблица 1: `companies`

### Назначение

Центральный реестр всех компаний / локальных ERP-экземпляров, управляемых через SUPERADMIN. Каждая запись — одна компания (одно юридическое лицо) со своей локальной ERP.

### Поля

| Поле | Тип | Обязательное | По умолчанию | Описание |
|---|---|---|---|---|
| `id` | INT UNSIGNED | Да | AUTO_INCREMENT | Первичный ключ |
| `key` | VARCHAR(50) | Да | — | Уникальный машинный идентификатор (slug). Используется в URL, путях папок, названиях БД. Только латиница, цифры, подчёркивание. Неизменяем после создания. Пример: `planex`, `company_a` |
| `name` | VARCHAR(255) | Да | — | Полное наименование компании (человекочитаемое) |
| `short_name` | VARCHAR(100) | Нет | NULL | Краткое наименование (опционально) |
| `entity_type` | VARCHAR(20) | Да | `legal_entity` | Тип юридического лица: `legal_entity` (ООО/АО), `ip` (ИП) |
| `status` | VARCHAR(20) | Да | `active` | Статус компании: `active` (работает), `inactive` (отключена), `suspended` (приостановлена), `provisioning` (в процессе создания) |
| `folder_path` | VARCHAR(255) | Нет | NULL | Путь к папке экземпляра ERP относительно корня проекта. Пример: `erp/planex/`. Может быть вычисляемым из `key`. |
| `db_identifier` | VARCHAR(100) | Нет | NULL | Имя БД или логический идентификатор для подключения. Пример: `erp_planex`. **НЕ содержит паролей, хоста, порта.** |
| `storage_path` | VARCHAR(255) | Нет | NULL | Путь к storage компании. Может быть вычисляемым из `folder_path`. |
| `settings_json` | JSON | Нет | NULL | Служебные настройки компании (таймзона, язык, региональные настройки). Расширяется по мере необходимости. |
| `created_at` | TIMESTAMP | Да | CURRENT_TIMESTAMP | Дата создания записи |
| `updated_at` | TIMESTAMP | Да | CURRENT_TIMESTAMP ON UPDATE | Дата последнего изменения |

### Индексы

| Индекс | Тип | Поля | Назначение |
|---|---|---|---|
| `PRIMARY` | PRIMARY KEY | `id` | Первичный ключ |
| `uk_key` | UNIQUE | `key` | Уникальность машинного идентификатора |
| `idx_status` | INDEX | `status` | Фильтрация по статусу |
| `idx_entity_type` | INDEX | `entity_type` | Фильтрация по типу юрлица |
| `idx_created_at` | INDEX | `created_at` | Сортировка по дате создания |

### Уникальные ограничения

- `key` — уникален в пределах таблицы, неизменяем после создания.

### Внешние ключи

Нет. `companies` — корневая таблица, на неё ссылается `company_features`.

### Статусы и переходы

```text
provisioning → active → suspended → active
                       → inactive

active → inactive (ручное отключение)
active → suspended (автоматическое или ручное)
suspended → active (восстановление)
inactive → active (повторное включение)
```

Переходы будут валидироваться на уровне приложения (не на уровне БД).

### Зарезервированные поля (будущие этапы)

| Поле | Когда понадобится |
|---|---|
| `logo_path` | Загрузка логотипа компании |
| `contact_email` | Контактный email компании для уведомлений |
| `contact_phone` | Контактный телефон |
| `address_json` | Юридический/фактический адрес |
| `tax_id` | ИНН |
| `registration_number` | ОГРН/ОГРНИП |
| `created_by_superadmin_user_id` | Кто из SUPERADMIN создал компанию |
| `deleted_at` | Мягкое удаление (soft delete) |

### Что входит в Stage 2 (первый этап миграций)

- Все поля, перечисленные в таблице выше.
- Все индексы.
- Статусная модель на уровне БД (ENUM `active`, `inactive`, `suspended`, `provisioning`).

### Что НЕ входит в Stage 2

- Зарезервированные поля (добавятся отдельными миграциями при необходимости).
- Реальные DB credentials (хост, порт, пользователь, пароль) — см. раздел «Безопасный подход к DB credentials».
- Автоматический provisioning новых ERP-инстансов.
- Валидация статусных переходов на уровне БД (только на уровне приложения).
- CRUD-операции (будут в Stage 3).

### Риски

- **`key` неизменяем.** Если потребуется переименовать `key`, потребуется ручное вмешательство: переименование папки, БД, обновление путей. Это осознанное архитектурное решение: `key` — фундаментальный идентификатор экземпляра.
- **`folder_path` и `db_identifier` могут рассинхронизироваться** с реальной файловой системой/БД, если создание экземпляра пройдёт с ошибкой. Нужна транзакционность provisioning.
- **JSON-поле `settings_json`** требует MySQL 5.7+. Если минимальная версия MySQL ниже, заменить на TEXT с JSON-валидацией на уровне приложения.

## Таблица 2: `features`

### Назначение

Реестр всех функций (features), доступных для включения/отключения по компаниям. Это единый каталог: модули, страницы, отчёты, custom-отчёты, действия, интеграции, UI-блоки.

### Поля

| Поле | Тип | Обязательное | По умолчанию | Описание |
|---|---|---|---|---|
| `id` | INT UNSIGNED | Да | AUTO_INCREMENT | Первичный ключ (технический) |
| `code` | VARCHAR(100) | Да | — | Уникальный машинный код. Только латиница, цифры, подчёркивание, точка. Примеры: `module.trips`, `page.finance_report`, `report.monthly_pnl`, `custom_report.client_abc`, `action.export_excel`, `integration.1c`, `ui_block.dashboard_widget` |
| `name` | VARCHAR(255) | Да | — | Человекочитаемое название |
| `type` | VARCHAR(20) | Да | — | Тип функции: `module`, `page`, `report`, `custom_report`, `action`, `integration`, `ui_block` |
| `description` | VARCHAR(500) | Нет | NULL | Описание функции |
| `parent_code` | VARCHAR(100) | Нет | NULL | Родительская feature. Например, `page.finance_report` имеет родителя `module.finance`. Иерархическая связь: страница/отчёт принадлежит модулю. |
| `is_system` | TINYINT(1) | Да | 0 | Системная функция (1) — нельзя удалить через UI SUPERADMIN. Например, базовые модули без которых ERP не работает. |
| `is_active` | TINYINT(1) | Да | 1 | Активна ли запись в реестре (0 = функция выведена из использования) |
| `sort_order` | INT | Да | 0 | Порядок сортировки в UI SUPERADMIN |
| `created_at` | TIMESTAMP | Да | CURRENT_TIMESTAMP | Дата создания |
| `updated_at` | TIMESTAMP | Да | CURRENT_TIMESTAMP ON UPDATE | Дата изменения |

### Индексы

| Индекс | Тип | Поля | Назначение |
|---|---|---|---|
| `PRIMARY` | PRIMARY KEY | `id` | Первичный ключ |
| `uk_code` | UNIQUE | `code` | Уникальность кода функции |
| `idx_type` | INDEX | `type` | Фильтрация по типу |
| `idx_parent_code` | INDEX | `parent_code` | Поиск дочерних функций |
| `idx_is_active` | INDEX | `is_active` | Фильтрация активных/неактивных |
| `idx_sort_order` | INDEX | `type`, `sort_order` | Сортировка в UI |

### Типы feature

| Тип | Назначение | Пример `code` |
|---|---|---|
| `module` | Бизнес-модуль (группа страниц, отчётов, действий) | `module.trips`, `module.clients`, `module.finance` |
| `page` | Конкретная страница внутри модуля | `page.trips_list`, `page.client_card` |
| `report` | Стандартный отчёт | `report.monthly_pnl`, `report.driver_stats` |
| `custom_report` | Кастомный отчёт (обычно только для одной компании) | `custom_report.client_abc_analysis` |
| `action` | Конкретное действие (кнопка, операция) | `action.bulk_update_status`, `action.export_excel` |
| `integration` | Интеграция с внешней системой | `integration.1c_accounting`, `integration.tracking_api` |
| `ui_block` | UI-блок/виджет | `ui_block.dashboard_fast_actions`, `ui_block.sidebar_widget` |

### Уникальные ограничения

- `code` — уникален в пределах таблицы.

### Внешние ключи

- `parent_code` ссылается на `features.code` (само-ссылка). На Stage 2 FK можно добавить как `ON DELETE SET NULL` (при удалении родительской функции дочерние не удаляются, а теряют родителя).

### Зарезервированные поля (будущие этапы)

| Поле | Когда понадобится |
|---|---|
| `icon` | Иконка для UI SUPERADMIN |
| `route_path` | Путь маршрута (для автоматической генерации навигации) |
| `required_permission_code` | Связанный permission (если feature требует конкретного права) |
| `config_json` | Дополнительная конфигурация (например, параметры custom-отчёта) |
| `tags` | Теги для группировки/поиска в UI |

### Что входит в Stage 2

- Все поля, перечисленные в таблице.
- Все индексы.
- Минимальный набор системных features (базовые модули будут добавлены на Stage 5).

### Что НЕ входит в Stage 2

- Зарезервированные поля.
- Предзаполнение реальными feature-кодами (это задача Stage 5: Feature toggles).
- Иерархическая логика (parent_code) на уровне приложения.
- UI управления features.

### Риски

- **Code naming convention.** Коды должны следовать единому шаблону (`type.name`). Нарушение конвенции усложнит автоматическую генерацию и проверки. Конвенция закрепляется здесь и сейчас.
- **parent_code — потенциальная сложность.** Иерархия feature может усложнить запросы и кэширование. На Stage 2 она закладывается структурно, но логика обхода иерархии будет реализована позже.
- **Удаление feature с дочерними.** При `ON DELETE SET NULL` дочерние функции потеряют родителя, но останутся в реестре. Если нужна каскадная деактивация — это логика приложения, не БД.

## Таблица 3: `company_features`

### Назначение

Связующая таблица (junction): какие функции включены для какой компании. Это и есть механизм feature toggles на уровне БД. Одна запись = одна функция, включённая (или выключенная) для одной компании.

### Поля

| Поле | Тип | Обязательное | По умолчанию | Описание |
|---|---|---|---|---|
| `id` | INT UNSIGNED | Да | AUTO_INCREMENT | Первичный ключ |
| `company_id` | INT UNSIGNED | Да | — | Ссылка на `companies.id` |
| `feature_code` | VARCHAR(100) | Да | — | Ссылка на `features.code` |
| `is_enabled` | TINYINT(1) | Да | 1 | Функция включена (1) или отключена (0) |
| `enabled_from` | TIMESTAMP | Нет | NULL | С какой даты/времени включена. NULL = с момента создания записи. |
| `enabled_until` | TIMESTAMP | Нет | NULL | До какой даты/времени включена. NULL = бессрочно. |
| `notes` | VARCHAR(500) | Нет | NULL | Комментарий: причина включения/отключения, номер заявки, кто запросил. |
| `created_at` | TIMESTAMP | Да | CURRENT_TIMESTAMP | Дата создания |
| `updated_at` | TIMESTAMP | Да | CURRENT_TIMESTAMP ON UPDATE | Дата изменения |

### Индексы

| Индекс | Тип | Поля | Назначение |
|---|---|---|---|
| `PRIMARY` | PRIMARY KEY | `id` | Первичный ключ |
| `uk_company_feature` | UNIQUE | `company_id`, `feature_code` | Одна компания — одна функция — одна запись |
| `idx_company_id` | INDEX | `company_id` | Все функции компании |
| `idx_feature_code` | INDEX | `feature_code` | Все компании с данной функцией |
| `idx_is_enabled` | INDEX | `is_enabled` | Фильтрация включённых/выключенных |
| `idx_enabled_until` | INDEX | `enabled_until` | Поиск истекающих доступов |

### Уникальные ограничения

- Пара `(company_id, feature_code)` уникальна. Не может быть двух записей для одной функции и одной компании.

### Внешние ключи

| FK | Ссылается на | ON DELETE | Обоснование |
|---|---|---|---|
| `company_id` | `companies.id` | CASCADE | При удалении компании удаляются все её feature-привязки |
| `feature_code` | `features.code` | CASCADE | При удалении функции из реестра удаляются все привязки |

### Логика включения/отключения

```text
Если записи нет:
  → функция НЕ доступна компании (по умолчанию всё выключено).

Если запись есть и is_enabled = 1:
  → функция доступна, если enabled_from <= NOW() и (enabled_until IS NULL OR enabled_until > NOW()).

Если запись есть и is_enabled = 0:
  → функция явно отключена (даже если есть enabled_from/until).
```

Модель «по умолчанию всё выключено» (default-deny) — самая безопасная. Компания получает только явно включённые функции.

### Что входит в Stage 2

- Все поля, индексы, внешние ключи.
- Базовая структура для дальнейшего заполнения.

### Что НЕ входит в Stage 2

- Кэширование в локальной ERP (таблица `local_feature_cache` — это локальная БД, не центральная).
- UI для включения/отключения функций.
- Автоматическая синхронизация feature между центральной БД и локальным кэшем.
- Логика проверки истечения срока (`enabled_until`) на уровне приложения.

### Риски

- **ON DELETE CASCADE для feature_code.** Если функция удалена из реестра `features`, все привязки компаний удалятся каскадно. Это осознанно: если функция больше не существует, привязки бессмысленны. Но требует осторожности при удалении функций.
- **Даты enabled_from/enabled_until и временные зоны.** TIMESTAMP в MySQL хранится в UTC. Приложение должно конвертировать в локальное время компании/пользователя.
- **Default-deny модель.** Удобна для безопасности, но требует явного включения всех нужных функций при создании компании. Потребуется механика «включить стандартный набор функций для новой компании» на Stage 5.

## Таблица 4: `superadmin_users`

### Назначение

Пользователи центральной панели SUPERADMIN. Полностью отделены от пользователей локальных ERP (таблица `users` в локальных БД). Разные таблицы, разные БД, разные сессии, разные права.

### Поля

| Поле | Тип | Обязательное | По умолчанию | Описание |
|---|---|---|---|---|
| `id` | INT UNSIGNED | Да | AUTO_INCREMENT | Первичный ключ |
| `name` | VARCHAR(255) | Да | — | Полное имя пользователя |
| `email` | VARCHAR(255) | Да | — | Email (используется для входа). Уникален. |
| `password_hash` | VARCHAR(255) | Да | — | Хэш пароля. Используется `password_hash()` PHP (bcrypt) с cost ≥ 12. |
| `role` | VARCHAR(50) | Да | `admin` | Роль внутри SUPERADMIN: `admin` (полный доступ), `operator` (ограниченный), `viewer` (только чтение). Зарезервировано: роли будут расширены. |
| `is_active` | TINYINT(1) | Да | 1 | Активен ли пользователь (0 = заблокирован) |
| `last_login_at` | TIMESTAMP | Нет | NULL | Дата/время последнего входа |
| `last_login_ip` | VARCHAR(45) | Нет | NULL | IP последнего входа (IPv4 или IPv6) |
| `created_at` | TIMESTAMP | Да | CURRENT_TIMESTAMP | Дата создания |
| `updated_at` | TIMESTAMP | Да | CURRENT_TIMESTAMP ON UPDATE | Дата изменения |

### Индексы

| Индекс | Тип | Поля | Назначение |
|---|---|---|---|
| `PRIMARY` | PRIMARY KEY | `id` | Первичный ключ |
| `uk_email` | UNIQUE | `email` | Уникальность email |
| `idx_is_active` | INDEX | `is_active` | Фильтрация активных/заблокированных |
| `idx_role` | INDEX | `role` | Фильтрация по роли |

### Роли (зарезервировано)

| Роль | Права |
|---|---|
| `admin` | Полный доступ ко всем функциям SUPERADMIN. Создание/удаление компаний, управление пользователями SUPERADMIN, feature toggles, системные настройки. |
| `operator` | Управление компаниями и feature toggles. Без доступа к системным настройкам и управлению пользователями SUPERADMIN. |
| `viewer` | Только просмотр. Без права изменений. |

Эти роли — зарезервированные значения. На Stage 2 они хранятся как VARCHAR. При необходимости будет создана отдельная таблица `superadmin_roles` и `superadmin_permissions` (аналогично локальной ERP).

### Внешние ключи

Нет. `superadmin_users` — независимая таблица.

### Зарезервированные поля (будущие этапы)

| Поле | Когда понадобится |
|---|---|
| `reset_token` | Токен сброса пароля |
| `reset_token_expires_at` | Срок действия токена сброса |
| `remember_token` | Токен «запомнить меня» |
| `email_verified_at` | Подтверждение email |
| `two_factor_secret` | 2FA секрет |
| `two_factor_enabled` | Флаг включения 2FA |
| `failed_login_attempts` | Счётчик неудачных попыток входа |
| `locked_until` | Блокировка до указанного времени |
| `avatar_path` | Путь к аватарке |

### Что входит в Stage 2

- Все поля, перечисленные в таблице.
- Все индексы.
- Поле `password_hash` — структура готова для хранения хэша.

### Что НЕ входит в Stage 2

- Реальная авторизация (login/logout/session).
- Сброс пароля.
- 2FA.
- Управление ролями и правами внутри SUPERADMIN.
- CRUD пользователей SUPERADMIN.
- Зарезервированные поля.
- Хранение реальных паролей или хэшей в MD-файлах (категорически запрещено).

### Риски

- **Алгоритм хэширования.** Используется PHP `password_hash()` с `PASSWORD_BCRYPT` (cost ≥ 12). Это стандарт. При переходе на argon2id в будущем нужно предусмотреть механизм перехэширования при входе.
- **Email как логин.** Удобно, но требует уникальности. Если email изменится — потребуется механизм смены email с подтверждением.
- **Отсутствие привязки к companies.** Пользователь SUPERADMIN управляет всеми компаниями. Если в будущем потребуется ограничить оператора конкретными компаниями, понадобится дополнительная связующая таблица `superadmin_user_companies`.

## Безопасный подход к DB credentials

### Проблема

Таблица `companies` должна идентифицировать БД компании, но **не должна хранить пароли, хосты, порты или пользователей БД**. Хранение секретов в БД — порочная практика.

### Решение

Разделение идентификации и аутентификации:

```text
┌─────────────────────────────────────────────────────────────┐
│  companies.db_identifier = "erp_planex"                     │
│  (только имя БД, НЕ пароль)                                  │
└─────────────────────────────────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────┐
│  Конфигурация подключения (НЕ в БД)                          │
│                                                             │
│  Вариант А: локальный .env экземпляра                        │
│    erp/planex/.env                                          │
│      DB_DATABASE=erp_planex                                 │
│      DB_HOST=127.0.0.1                                      │
│      DB_PORT=3306                                           │
│      DB_USERNAME=erp_app                                    │
│      DB_PASSWORD=***                                        │
│                                                             │
│  Вариант Б: центральный конфигурационный файл                │
│    config/companies.php (в .gitignore!)                     │
│      'planex' => [                                          │
│        'database' => 'erp_planex',                          │
│        'host'     => '127.0.0.1',                           │
│        'username'  => 'erp_app',                            │
│        'password'  => '***',                                │
│      ]                                                      │
│                                                             │
│  Вариант В: HashiCorp Vault / AWS Secrets Manager           │
│    (для production, за пределами Stage 2)                    │
└─────────────────────────────────────────────────────────────┘
```

### Принципы

1. **`companies.db_identifier`** хранит только логический идентификатор БД (например, имя БД). Не пароль, не хост, не пользователя.
2. **Реальные credentials** хранятся либо в локальном `.env` экземпляра ERP, либо в центральном конфигурационном файле, исключённом из git (`.gitignore`).
3. **SUPERADMIN при создании компании** генерирует пароль БД, создаёт пользователя MySQL с ограниченными правами (только к своей БД), записывает credentials в `.env` компании. Пароль при этом не попадает в БД SUPERADMIN.
4. **Конфигурационный файл** (если используется вариант Б) должен быть в `.gitignore` и никогда не коммититься.
5. **В production** рекомендуется использовать Vault или аналогичный сервис управления секретами.

### Что гарантирует этот подход

- Даже при полной компрометации БД SUPERADMIN злоумышленник не получит пароли к БД компаний.
- Таблица `companies` остаётся безопасной для хранения в git (через миграции).
- MD-файлы не содержат реальных паролей.

## Feature toggles: цепочка проверки

В будущем (Stage 5) локальная ERP будет проверять доступность функции по цепочке:

```text
1. Локальный кэш (local_feature_cache) — быстро, без запроса к SUPERADMIN
2. Если кэш устарел — запрос к центральной БД (company_features)
3. Проверка: is_enabled = 1 AND (enabled_from IS NULL OR NOW() >= enabled_from) AND (enabled_until IS NULL OR NOW() < enabled_until)
4. Если feature доступна → проверка permissions роли пользователя
5. Если всё OK → показать страницу / выполнить действие
```

На Stage 2 эта логика не реализуется. Таблицы создаются как структурная основа для будущей реализации.
