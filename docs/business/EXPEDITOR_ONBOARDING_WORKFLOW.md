# ERP PLANEX — EXPEDITOR_ONBOARDING_WORKFLOW

## Назначение

Этот документ фиксирует утверждённый владельцем путь развития системы после принятия текущей точки `/superadmin`.

Цель ближайшего функционального цикла:

```text
SUPERADMIN создает экспедитора
→ SUPERADMIN создает главного пользователя экспедитора
→ главный пользователь создает локального логиста
→ логист ведет клиентов, подрядчиков, машины, водителей и связки
```

## Утвержденные термины

### Экспедитор

В терминах системы экспедитор — это отдельная локальная ERP / компания, которую создает `SUPERADMIN`.

Создание экспедитора включает:
- запись в центральной БД SUPERADMIN;
- автоматическое создание локальной БД экспедитора;
- автоматическое создание отдельной папки хранения загруженных документов.

Кодовая база, PHP-скрипты, CSS, JS, общие миграционные механизмы и системные файлы не копируются в папку экспедитора. Они остаются общими.

### Главный пользователь экспедитора

Главный пользователь экспедитора — это роль `Руководитель`.

Правила:
- создается `SUPERADMIN`;
- создается отдельным действием после создания экспедитора;
- хранится в центральной БД SUPERADMIN;
- привязывается к конкретному экспедитору / компании;
- входит через общий логин;
- после входа попадает в локальную ERP своего экспедитора.

### Локальный пользователь

Локальные пользователи экспедитора хранятся в локальной БД экспедитора.

Первый локальный пользовательский сценарий:
- `Руководитель` создает пользователя с ролью `Логист`.

### Клиент и подрядчик

Используются термины:
- `клиент`;
- `подрядчик`.

Термин `перевозчик` на первом этапе не вводится как отдельная сущность.

Клиенты и подрядчики хранятся в отдельных справочниках, таблицах и формах. Общая таблица `counterparties` с типом на этом этапе не используется.

## Последовательность разработки

### Шаг 1. SUPERADMIN Companies Registry

Создать основу управления экспедиторами в `/superadmin`.

Функции этапа:
- список экспедиторов / локальных ERP;
- создание экспедитора;
- автоматическое создание записи в центральной БД;
- автоматическое создание локальной БД;
- автоматическое создание папки документов;
- отображение статуса экспедитора;
- обработка ошибки provisioning без частично скрытых состояний.

Технические детали схемы БД и provisioning-команды должны быть уточнены отдельной архитектурной задачей перед кодингом.

### Шаг 2. Главный пользователь экспедитора

После создания экспедитора `SUPERADMIN` отдельным действием создает главного пользователя.

Функции этапа:
- форма создания главного пользователя;
- привязка пользователя к экспедитору;
- роль `Руководитель`;
- хранение пользователя в центральной БД;
- вход через общий логин;
- маршрутизация в локальную ERP экспедитора после входа.

Поля пользователя, правила пароля, сброса пароля и уведомлений требуют отдельного уточнения перед реализацией.

### Шаг 3. Локальные пользователи экспедитора

`Руководитель` внутри своей локальной ERP создает локальных пользователей.

Первый утвержденный локальный пользователь:
- роль `Логист`.

Логист работает только внутри локальной БД своего экспедитора.

### Шаг 4. Справочник клиентов

Логист ведет клиентов в локальной БД экспедитора.

Поля клиента:
- `name` — наименование, обязательное поле;
- `inn` — ИНН, обязательное поле;
- `kpp` — КПП;
- `ogrn` — ОГРН;
- `legal_address` — юридический адрес;
- `physical_address` — фактический адрес;
- `contact_person` — контактное лицо;
- `contact_phone` — телефон;
- `contact_email` — email;
- `status` — `active`, `blocked`, `archive`;
- `comments` — комментарий.

Документы клиента отображаются в карточке редактирования:
- название;
- тип;
- дата загрузки;
- комментарий;
- действия: изменить / удалить;
- ссылка на файл, если есть `file_path`.

### Шаг 5. Справочник подрядчиков

Логист ведет подрядчиков в локальной БД экспедитора.

Набор полей на первом этапе совпадает с клиентом, но справочник, таблица и формы отдельные:
- `name` — наименование, обязательное поле;
- `inn` — ИНН, обязательное поле;
- `kpp` — КПП;
- `ogrn` — ОГРН;
- `legal_address` — юридический адрес;
- `physical_address` — фактический адрес;
- `contact_person` — контактное лицо;
- `contact_phone` — телефон;
- `contact_email` — email;
- `status` — `active`, `blocked`, `archive`;
- `comments` — комментарий.

Документы подрядчика отображаются по тому же принципу, что документы клиента.

### Шаг 6. Справочник транспорта

Логист ведет машины в локальной БД экспедитора.

Поля тягача:
- `truck_plate` — госномер тягача, обязательное поле;
- `truck_brand` — марка тягача, обязательное поле;
- `truck_model` — модель тягача;
- `truck_vin` — VIN тягача, обязательное поле;
- `truck_load_capacity` — грузоподъемность тягача, тонн, обязательное поле;
- `truck_body_volume` — объем кузова тягача, м3, обязательное поле;
- `has_trailer` — признак "Есть полуприцеп".

Поля прицепа / полуприцепа показываются, если включен `has_trailer`:
- `trailer_plate` — госномер прицепа / полуприцепа;
- `trailer_brand` — марка прицепа / полуприцепа;
- `trailer_model` — модель прицепа / полуприцепа;
- `trailer_vin` — VIN прицепа / полуприцепа;
- `trailer_load_capacity` — грузоподъемность прицепа / полуприцепа, тонн;
- `trailer_body_volume` — объем кузова прицепа / полуприцепа, м3.

Дополнительные поля:
- `status` — `active`, `blocked`, `archive`;
- `comments` — комментарий.

Файлы по тягачу:
- СТС — `typed_files[sts][]`;
- диагностическая карта — `typed_files[diagnostic_card][]`;
- фото машины — `typed_files[truck_photo][]`.

Файлы по полуприцепу:
- СТС полуприцепа — `typed_files[trailer_sts][]`;
- диагностическая карта полуприцепа — `typed_files[trailer_diagnostic_card][]`;
- фото полуприцепа — `typed_files[trailer_photo][]`.

Прочие файлы:
- прочие файлы — `typed_files[other][]`;
- комментарий к прочим файлам — `comments[other]`.

### Шаг 7. Справочник водителей

Логист ведет водителей в локальной БД экспедитора.

Поля водителя:
- `full_name` — ФИО, обязательное поле;
- `phone` — телефон, обязательное поле;
- `passport_number` — номер паспорта, обязательное поле;
- `passport_issue_date` — дата выдачи паспорта, обязательное поле;
- `passport_issued_by` — кем выдан паспорт, обязательное поле;
- `license_number` — номер водительского удостоверения, обязательное поле;
- `license_issue_date` — дата выдачи водительского удостоверения, обязательное поле;
- `snils` — СНИЛС, обязательное поле;
- `comments` — комментарий;
- `status` — `active`, `blocked`, `archive`.

Документы водителя:
- водительское удостоверение — `driver_license`;
- паспорт — `driver_passport`;
- СНИЛС — `driver_snils`;
- фото — `driver_photo`.

Для каждого документа показывается:
- статус "Загружен" / "Не загружен";
- имя файла;
- дата загрузки;
- кнопка скачивания.

Загрузка идет через форму с:
- `entity_type = driver`;
- `doc_type`;
- поле файла `file`.

### Шаг 8. Связки / экипажи

Логист формирует связки:

```text
подрядчик + машина + водитель
```

Эта связка соответствует ранее принятому правилу:

```text
Экипаж = Подрядчик + жесткая пара (Машина + Водитель)
```

Если водитель переходит на другую машину, создается новая связка / экипаж.

## Что не реализуется в этом цикле

- рейсы и заявки;
- бухгалтерия;
- налоговая логика;
- юридические проверки документов;
- отдельная сущность `перевозчик`;
- сложные роли кроме `Руководитель` и `Логист`;
- отдельная кодовая копия ERP для каждого экспедитора;
- дизайн-приемка Главным дизайнером / КЛАУД как блокирующий фактор.

## Уточнения перед первым кодингом — 2026-06-13

Владелец утвердил 3 обязательных технических ответа для первого модуля `SUPERADMIN Companies Registry`:

1. Поля создания экспедитора: на первом этапе использовать стандартный набор как у клиента/подрядчика, но экспедитор должен быть отдельной SUPERADMIN-сущностью / таблицей, не локальным подрядчиком.
2. Имя локальной БД: генерируется автоматически из `ID компании`; вручную не вводится.
3. Storage-папка: называется / генерируется по `ID компании`.

Базовые поля создания экспедитора:
- `name` — наименование, обязательное поле;
- `inn` — ИНН, обязательное поле;
- `kpp` — КПП;
- `ogrn` — ОГРН;
- `legal_address` — юридический адрес;
- `physical_address` — фактический адрес;
- `contact_person` — контактное лицо;
- `contact_phone` — телефон;
- `contact_email` — email;
- `status` — статус;
- `comments` — комментарий.

Остаются открытыми для отдельных будущих задач, но не блокируют первый Companies Registry skeleton:
