# ERP PLANEX — DESIGN_CODE_INTEGRATION

## Назначение

Этот файл — главный UI/UX и дизайн-код регламент ERP PLANEX.

Он заменяет отдельный `UI_UX_RULES.md`. Отдельный файл `UI_UX_RULES.md` удалён как дублирующий и не должен восстанавливаться.

Цель файла — зафиксировать единый UI-фундамент, правила работы дизайнера, правила передачи UI-задач кодеру и правила QA-приёмки интерфейсов.

---

## Источник истины по UI

Для UI действуют следующие источники:

```text
docs/ui/DESIGN_CODE_INTEGRATION.md   # главный UI-регламент
docs/ui/STYLE_ERP_EXTRACTED_RULES.md # формализованные правила из STYLE ERP
docs/ui/ERP_UI_KIT_CORE.html         # основной компактный UI-kit: CORE modules + COMPOSITE patterns
docs/ui/ERP_UI_MODULE_CATALOG.html   # legacy extraction draft / большой черновой каталог
docs/ui/PAGE_PATTERN.md              # общий стандарт страницы
docs/ui/FORMS_STANDARD.md            # стандарт форм
docs/ui/TABLES_STANDARD.md           # стандарт таблиц
docs/ui/pages/                       # MD-шаблоны конкретных страниц
```

Запрещено создавать второй общий UI-регламент с тем же смыслом.

`STYLE_ERP_EXTRACTED_RULES.md` — не runtime-библиотека и не библиотека компонентов. Это формализованные правила из визуальных образцов `C:\Users\Vladimir\Desktop\PLANEX\SITE\STYLE ERP\`.

Кодер не должен открывать STYLE ERP и выбирать оттуда блоки. Если правило нужно для реализации, оно должно быть перенесено в MD/handoff до передачи задачи кодеру.

`ERP_UI_KIT_CORE.html` является основным обязательным источником для `erp-uiux-designer`. Дизайнер проектирует страницу из CORE modules и COMPOSITE patterns, а не из разрозненного списка extraction-пунктов.

`ERP_UI_MODULE_CATALOG.html` остаётся legacy extraction draft / историей извлечения 224 пунктов из STYLE ERP. Он не является основным рабочим каталогом для дизайнера.

Новый UI-модуль нельзя использовать в page handoff и нельзя отдавать кодеру, пока модуль не формализован в Core Kit / профильных MD. Если подходящего модуля нет, дизайнер обязан остановиться:

```text
BLOCKED: NEEDS_UI_MODULE_EXPANSION
```

Page handoff обязан содержать раздел `CORE modules used`, выбранный `COMPOSITE pattern`, а также `MODULE USAGE DECISIONS` с причинами выбора и отказа от альтернатив.

Private applied examples не являются названиями универсальных модулей. Запрещено использовать page-specific module names as universal handoff names.

## Главный принцип

ERP PLANEX — рабочая ERP для сотрудников логистики.

Интерфейс должен быть:

- строгим;
- плотным;
- понятным;
- предсказуемым;
- удобным для ежедневной работы;
- безопасным для runtime и дальнейшей агентной разработки.

Это не лендинг, не промо-сайт, не SaaS-dashboard и не набор случайных Bootstrap-страниц.

## Роли в UI-workflow

### erp-architect

Архитектор перед каждой задачей определяет, затрагивает ли задача UI.

Если задача затрагивает страницу, форму, таблицу, карточку, навигацию, фильтры, статусы, empty/loading/error states, модалку, inspector или пользовательский сценарий — сначала подключается дизайнер.

### erp-uiux-designer

Дизайнер обязан создать или обновить MD-шаблон страницы в:

```text
docs/ui/pages/
```

MD-шаблон страницы — источник истины для кодера и QA.

### erp-coder

Кодер реализует UI строго по MD-шаблону страницы.

Кодер не должен сам придумывать layout, CSS-классы, порядок блоков, состав формы, UX-поведение или визуальные состояния.

Если задача затрагивает UI, но актуального MD-шаблона нет, кодер обязан остановиться со статусом:

```text
BLOCKED: NEEDS_UI_DESIGN_HANDOFF
```

### erp-qa-tester

QA проверяет реализацию по:

- задаче архитектора;
- актуальному MD-шаблону страницы;
- этому UI-регламенту;
- `PAGE_PATTERN.md`;
- `FORMS_STANDARD.md`;
- `TABLES_STANDARD.md`.

## Обязательный workflow UI-задачи

```text
Владелец / задача
→ erp-architect
→ erp-uiux-designer создаёт или обновляет docs/ui/pages/[page-name].md
→ erp-coder реализует строго по MD-шаблону
→ erp-qa-tester проверяет соответствие шаблону
→ erp-architect принимает или запускает второй круг
```

Архитектор не принимает UI-задачу как `DONE`, если:

- нет актуального MD-шаблона страницы;
- кодер реализовал UI не по шаблону;
- QA не проверил соответствие шаблону;
- не обновлены нужные MD и логи.

## Когда дизайнер обязателен

Дизайнер обязателен, если задача затрагивает:

- новую страницу;
- новый модуль с интерфейсом;
- новую форму;
- новую таблицу;
- карточку сущности;
- навигацию;
- меню;
- фильтры;
- поиск;
- статусы;
- пустые состояния;
- ошибки;
- подтверждения действий;
- UX-сценарий;
- расположение блоков;
- визуальную структуру;
- адаптив;
- изменение существующей страницы.

Если есть сомнение, дизайнер подключается.

## Когда дизайнер не нужен

Дизайнер не нужен для чисто технических задач без UI:

- PDO-обёртка;
- роутер;
- backend-сервис;
- repository/model;
- конфигурация;
- исправление PHP-ошибки;
- технический рефакторинг без изменения UI;
- документация без изменения интерфейса;
- инфраструктурная задача.

## STYLE ERP Extracted Rules

Визуальные образцы STYLE ERP формализованы в:

```text
docs/ui/STYLE_ERP_EXTRACTED_RULES.md
```

Дизайнер обязан использовать этот документ при production-grade handoff для важных UI-экранов.

Вместе с этим документом дизайнер обязан использовать визуальный каталог:

```text
docs/ui/ERP_UI_KIT_CORE.html
```

Извлечённые ключевые правила:

- desktop-first app shell: sidebar 224px, topbar 38px, min-width 1440px;
- visual direction: Industrial Graphite + Warm Accent;
- canonical tokens для nav/surfaces/lines/text/accent/status/controls;
- плотная типографика: IBM Plex Sans, body 13px, tabular nums;
- ERP-grid как основной объект списков: sticky thead, row 32px, row actions on hover;
- unified forms: 28px controls, field labels, error/success/disabled states;
- filters-bar компактный, без больших filter cards;
- inspector 320-380px для list+detail сценариев;
- key-value blocks для системной/admin информации;
- admin/settings pages: sections, tables/forms/key-value, no KPI/SaaS cards;
- empty/loading/error states должны быть осмысленными и page-specific;
- charts используются только для report/analytics, не вместо рабочих таблиц.

STYLE ERP showcase pages не являются production layouts. Дизайнер не должен превращать showcase композицию в рабочую страницу.

## Общий стандарт страницы

Каждая рабочая страница должна иметь:

- понятный заголовок;
- назначение страницы;
- главное действие;
- фильтры или поиск, если нужны;
- таблицу, форму или рабочую область;
- видимые статусы;
- empty state;
- error state;
- loading state, если есть загрузка;
- подтверждение опасных действий;
- понятные сообщения пользователю.

## Запреты UI

Запрещено:

- делать лендинг вместо рабочей ERP;
- делать SaaS-dashboard ради красоты;
- создавать разрозненные стили на каждой странице;
- использовать Bootstrap/Tailwind/Material UI/React/Vue без отдельного решения;
- использовать случайные цвета без токенов;
- использовать случайные CSS-классы;
- показывать обычному пользователю технические ошибки;
- прятать важные статусы;
- делать опасные действия без подтверждения;
- загружать документы в `public`;
- смешивать HTML, SQL и бизнес-логику;
- **demo-placeholder UI**: псевдоиконки `[=]`, `[#]`, `[~]`, `[v]`; emoji/символы как временные иконки; карточный SaaS-dashboard там, где нужна ERP/settings/admin страница; большие пустоты; blue/white corporate UI; случайные цвета; случайные CSS-классы; debug badges как основной визуальный элемент;
- `border-radius > 4px` для новых элементов;
- `box-shadow blur > 8px` для новых элементов;
- Bootstrap/Tailwind/Material классы;
- inline styles, кроме динамических PHP-значений вида `style="width: <?= $pct ?>%"`.

---

## Обязательные UX-принципы

- На странице должно быть понятно, что делать дальше.
- Таблицы должны быть читаемыми.
- Формы должны иметь понятные labels.
- Обязательные поля должны быть явно отмечены.
- Ошибки должны быть написаны человеческим языком.
- У опасных действий должно быть подтверждение.
- Пустые состояния должны объяснять причину и следующий шаг.
- Статусы должны быть видимыми и единообразными.
- Частые действия должны быть доступны без лишних кликов.
- Интерфейс должен быть удобен для руководителя, логиста, менеджера, бухгалтера и back-office.

## MD-шаблоны страниц

Для каждой новой или изменяемой страницы дизайнер создаёт/обновляет файл:

```text
docs/ui/pages/[page-name].md
```

Шаблон должен содержать:

1. Название страницы.
2. Назначение.
3. Пользователь/роль.
4. Основной сценарий.
5. Структура страницы сверху вниз.
6. Layout pattern.
7. Блоки.
8. Формы и поля.
9. Таблицы и колонки.
10. Кнопки и действия.
11. Статусы.
12. Empty/loading/error states.
13. Ошибки и валидация.
14. Подтверждения опасных действий.
15. Адаптивное поведение.
16. Используемые UI-компоненты/classes.
17. Что кодеру запрещено менять.
18. Чеклист QA-приёмки.

Базовый шаблон лежит в:

```text
docs/ui/pages/_PAGE_TEMPLATE.md
```

## Правила для KILO при UI-задачах

KILO обязан:

- читать этот файл перед UI-задачей;
- читать MD-шаблон конкретной страницы;
- не создавать отдельные стили для каждой страницы;
- не смешивать бизнес-логику и HTML;
- не писать SQL во view;
- не добавлять страницу без `feature_code` после старта бизнес-модулей;
- обновлять UI-документацию при изменении дизайн-стандарта;
- обновлять `ERP_PLANEX_CONTEXT_FOR_NEW_CHAT.md`, если изменился UI-фундамент, workflow или структура проекта.
