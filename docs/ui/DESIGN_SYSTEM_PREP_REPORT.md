# Design System Prep Report

## Что изучено

Полностью разобран `FINAL3.html` (3023 строки, inline `<style>` ~83 700 символов / 605 CSS-правил). Файл оказался гибридным: он одновременно (1) содержит системные production-классы интерфейса ERP и (2) является самой витриной-референсом (с обёрткой `.reference-section`, `.sc-card`, `.ai-note`, `.do-not-change` и т.п. для показа компонентов человеку/агенту). Эти два слоя были разделены вручную и автоматической фильтрацией по списку из 47 wrapper-классов.

## Какие файлы созданы

- `public/assets/css/erp-ui.css` — 605 правил, без изменения цветов/радиусов/теней/типографики, с заголовком-преамбулой о происхождении.
- `docs/ui/DESIGN_STANDARD.md` — нормативный документ для кодера.
- `docs/ui/DESIGN_SYSTEM_PREP_REPORT.md` — этот отчёт.

## Какие группы компонентов вынесены

Layout/shell, sidebar (вкл. подменю, счётчики, состояния active/parent/open), topbar, page header, table-card, panel-section, формы (field/input/select/textarea), специализированные поля (custom-select, multiselect, entity-lookup, date, number, masked, clearable), кнопки (primary/secondary/ghost/toolbar/danger/icon), badge, doc-status, flight-status, form-alert, row-actions, empty-state, modal (sm/md/lg + confirm/warning/info варианты), toast, filters-bar, pagination, tabs, skeleton, stepper, context-menu, tooltip.

## Что покрыто полностью

Все 21 группа компонентов из задачи присутствуют в `erp-ui.css` и были явно проверены построчно. Responsive-поведение зафиксировано в двух `@media`-точках (1439px, 700px).

## Требует будущей дизайнерской доработки (DESIGN_TODO)

1. **Нет универсальной generic-карточки.** В FINAL3 есть только специализированные `.table-card` (для таблиц) и `.chart-card` (для графиков) — обычной карточки для произвольного контента (текст + заголовок, не таблица и не график) нет. Кодеру придётся брать `.panel-section` как ближайший паттерн до отдельного решения дизайнера.
2. **Расхождение в responsive-стратегии.** Текстовое правило в самом FINAL3 ("390 critical only", "sidebar не должен ломать контент") не совпадает с фактическим CSS: на 700px sidebar получает `display:none` целиком, а не превращается в управляемый critical-fallback. Нужно решение дизайнера — либо менять CSS, либо менять текст правила.
3. **Дублирующее определение `.content`.** В исходнике `.content` было объявлено дважды с разными свойствами (`align-items:initial` версия — особенность только reference-страницы). Для erp-ui.css оставлена единственная чистая версия; если в реальных ERP-страницах ожидалось центрирование placeholder-контента — это нужно явно зафиксировать отдельным классом, а не через `.content`.
4. Любой новый UI-компонент, не покрытый списком выше, кодер обязан помечать `DESIGN_TODO` по правилам из `DESIGN_STANDARD.md`, а не придумывать стиль самостоятельно.

## Риски для кодера

- Если кодер по ошибке подключит сам `FINAL3.html` как источник CSS (а не `erp-ui.css`), он получит вместе с системными стилями весь reference-wrapper CSS (`.reference-*`, `.sc-*` и т.д.), что раздует страницу и может конфликтовать с реальной разметкой ERP. Подключать нужно только `erp-ui.css`.
- Токены `--alert-*` и `--badge-*` — это намеренно отдельный от `--success/--warning/--danger` словарь (источник цвета — палитра графиков, не семантические токены). Кодеру нельзя смешивать их между собой при создании новых компонентов.
- `.doc-status` и `.badge` — раздельные словари классов с похожим назначением (статусы); их нельзя смешивать в одном ряду (зафиксировано отдельным правилом в комментарии CSS).

## Следующий шаг для кодера

1. Подключить `public/assets/css/erp-ui.css` на всех страницах ERP вместо любых текущих inline-стилей или разрозненных CSS.
2. Заменить существующую вёрстку на классы из таблицы в `DESIGN_STANDARD.md`, не меняя HTML-структуру там, где она уже соответствует утверждённым паттернам.
3. Любые новые экраны верстать только этими классами; при нехватке компонента — `DESIGN_TODO` + ближайший паттерн, не самодеятельность.
