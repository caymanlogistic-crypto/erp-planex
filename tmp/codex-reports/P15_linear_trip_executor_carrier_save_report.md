# P15 — Исполнитель рейса, перевозчик и сохранение линейного рейса

## Финальный статус

`RUNTIME_ACCEPTED`

На живом `https://plan-ex.ru/erpv2/` под ролью `company_owner` подтверждено:

- форма редактирования линейного рейса открывается;
- самостоятельное поле «Перевозчик» скрыто;
- `carrier_contractor_id` определяется по `contractor_id` выбранного исполнителя рейса;
- исторические условия оплаты корректно преобразуются в современные значения формы;
- неизменённая форма успешно сохраняется;
- POST возвращает HTTP 200 и JSON `success=true`;
- сервер возвращает сообщение `Рейс успешно сохранён.`;
- транзакция не завершается внутренней ошибкой.

## Исходные дефекты

### D1. Дублирующее обязательное поле «Перевозчик»

В форме одновременно требовалось выбрать:

1. перевозчика;
2. исполнителя рейса.

При этом исполнитель рейса уже является экипажем, связанным с перевозчиком через `contractor_id`. Независимый выбор создавал возможность рассинхронизации и заставлял пользователя повторно вводить одну сущность.

### D2. Внутренняя ошибка при сохранении

`LinearTripEditSaveService::parsePaymentRows()` формировал только современные поля:

- `condition_type`;
- `days_count`;
- `days_kind`.

Но `LinearRouteService::storeRoutePayments()` продолжал читать совместимые legacy-ключи:

- `payment_due_type`;
- `payment_due_days`;
- `payment_due_days_kind`.

Отсутствующие ключи приводили к исключению, rollback транзакции и ответу `internal_save_error`.

### D3. Некорректное преобразование старой предоплаты

Старое значение `Предоплата на загрузке` было первоначально преобразовано в современное `prepayment`. В текущей модели `prepayment` требует отдельную конкретную дату, поэтому неизменённая историческая запись не проходила валидацию. Старое значение по смыслу соответствует `start_day` — оплате в день начала рейса.

## Выполненные изменения

### Серверная нормализация перевозчика

Создан `App\Service\LinearTripRequestNormalizer`.

Метод `deriveCarrierFromExecutor()`:

1. получает `route_executor_id` из POST;
2. открывает БД текущей компании;
3. использует `LinearRouteService::fetchVisibleRouteExecutors()` с учётом роли пользователя;
4. находит доступного исполнителя;
5. записывает в POST его `contractor_id` как `carrier_contractor_id`;
6. не доверяет присланному клиентом самостоятельному значению перевозчика.

Нормализация подключена перед созданием и редактированием рейса в `LinearTripController`.

### Интерфейс

Добавлен `public/assets/js/linear-trip-executor-carrier.js`:

- поле перевозчика скрывается в формах создания и редактирования;
- при выборе исполнителя резервно синхронизируется скрытое значение;
- сервер остаётся единственным доверенным источником связи исполнитель → перевозчик.

### Условия оплаты

`normalizeRoutePaymentConditions()` преобразует исторические значения:

- `Предоплата на загрузке` → `start_day`;
- `После загрузки` → `after_start`;
- `До выгрузки` → `end_day`;
- `После выгрузки` → `after_end`;
- остальные поддерживаемые legacy-условия — в соответствующие современные значения.

### Совместимость сохранения

`LinearTripEditSaveService::parsePaymentRows()` теперь одновременно формирует современные и legacy-поля оплаты. Это устраняет undefined-key failure и сохраняет совместимость существующего финансового контура.

### Диагностика

Для неожиданных ошибок POST добавлен безопасный `error_id` и отдельный журнал `storage/logs/P15_linear_trip_save_errors.log`. Пользователю не раскрываются SQL, пути или stack trace; полная техническая информация остаётся на сервере.

## Ограничения и риски

- Поле перевозчика остаётся в DOM как скрытое compatibility-поле для старой формы, но сервер игнорирует его как источник истины и вычисляет значение заново.

- Живой тест выполнил сохранение существующих значений рейса №2; бизнес-данные намеренно не изменялись.
